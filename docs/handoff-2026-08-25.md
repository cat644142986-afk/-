## 1. 先确认产品定位，不要把它做成普通图片工具

Product Atelier 是一个高级、克制、知识库驱动、可解释、能从用户评审与终稿中成长的 AI 设计师伙伴。必须遵守的产品原则：

1. 知识库要在创作前、执行中、结果评审后真实介入。
2. 用户的采用/拒绝/修改/终稿差异/自然语言反馈要形成可追溯证据，但未经确认不得自动修改正式知识。
3. 主界面信息做减法：一屏一个主要问题、一个最强 CTA、默认智能、细节按需展开。
4. 中文承担全部核心含义；英文只做短眉题、状态标签、视觉装饰。删除英文后仍能完整操作。
5. UI 以专业设计软件标准验收，不能靠堆叠卡片、渐变、发光、大圆角制造表面效果。
6. 后台任务不因切换工作流而停止；返回原工作流必须恢复素材/选择/参数/任务/进度/结果/评审现场。
7. 不允许让用户再次发现基础问题后才修复；每个检查点先由开发侧完成真实数据、异常态、窄屏、DPI、重启测试。
8. 功能增加不能造成首屏信息爆炸；多工作流必须并发且现场可恢复。
9. 不引入 Cordis/Node 智能体运行时；不加常驻聊天栏、Shell、子代理系统。

### 3.1 提交 `1cdefc4` feat: close feedback-to-generation loop and finish v1.1 defect sweep

核心是把“反馈→生成”真正闭环。

## 4. 我今天引入的问题（接手者务必知道）

### 4.1 回归：renderQueue 漏写 innerHTML（已在 84ce7eb 修复）

现象：上传素材后看不到预览图，且主工作区出现多张空的“+ 添加图片”卡片（截图里是 4 张）。

根因：`1cdefc4` 里把 `queue.innerHTML = state.assets.map(...)` 重构成 `const items = state.assets.map(...)`，但没有把 `items` 写回 `queue.innerHTML`。于是素材卡片从未渲染，`queue.innerHTML +=`（加“添加图片”入口）却在每次 `renderQueue()` 调用时不断追加，造成多张空卡。

为什么此前测试没拦住：前端 Node 测试是静态回归 + 纯函数测试，不驱动 DOM，覆盖不到“innerHTML 赋值是否写回”这类交互渲染缺陷；后端测试与本问题无关。

修复：`queue.innerHTML = items;` 恢复，附静态防回归断言。

### 4.2 应吸取的教训（写给下一个模型）

1. 改 DOM 渲染逻辑时，任何“先计算字符串再写入”的重构，都必须确认 `innerHTML = <字符串>` 确实发生，并加静态断言。
2. 任何“添加一个入口/按钮”的改动，要考虑重复调用会不会累积。
3. 覆盖桌面快捷方式/便携 EXE 之前，必须先跑自动测试 + 真机验证。今天是先覆盖后验证，属流程违规。
4. 每次新对话必须按交接文档先读知识库三个核心文件 + 交接文档，不要凭上一轮总结往下推。这是今天被用户批评的核心。

## 6. 剩余 BUG / 隐患（含代码位置）

1. “查看生成依据”对已完成/历史任务绑定的是实时知识，不是该任务实际用的知识。
   - `src/js/app.js` `openJobResults()`：只调用 `openJobWorkspace(job,false)` 触发 `compileKnowledgePreview`（当前意图的实时编译），未把该任务的 `applied_knowledge/execution_traces` 写入 `state.knowledgeBundle`。
   - `openSessionFromHistory()`：`positive_rules: [], negative_rules: [], conflicts: []`，只放 `knowledge_refs` 来源。→“本次到底用了哪几条规则”不可复现。
2. 对比图对齐（#3）：`compare-view > img` 与 `.compare-after img` 均 `object-fit:contain`；原图（竖幅产品照）与结果（多为 1:1）缩放居中后滑块两侧可能不重合。需真机非方形原图复测。
3. 数字语义分叉（#8）：`renderFileMeta()` 中 `asset-count` 用 `state.assets.length`（总数），`ready-count` 用选中数；并排显示易被误解。
4. toast 上限 3 条 + 1800ms：批量删除/反馈时较早的重要提示会被顶掉。
5. `assetUrl` 时序依赖：缩略图需 `hydrateAssetUrls` 先跑拿到绝对地址；主路径（`loadWorkspace` 先 hydrate 再 `renderQueue`）正确，但非所有调用 `renderQueue` 的路径都保证先 hydrate，可能短暂用相对地址破图。建议逐条调用点确认。
6. 结果态流程指引：见第 5 节 #16/#17。
